# ทีละขั้น · Step by step — จาก Terminal ถึง PR ที่ถูกรวม

**หน้านี้คือ "ทำยังไง" ทีละคำสั่ง** ตั้งแต่เปิด Terminal ครั้งแรก จนการแก้ของคุณถูกรวมเข้า
`main` และขึ้นเว็บจริง อ่านไล่จากบนลงล่างครั้งเดียว แล้วครั้งต่อไปกลับมาดูเฉพาะขั้นที่ลืม

> **หน้านี้กับ [CONTRIBUTE](/CONTRIBUTE) แบ่งกันคนละหน้าที่ และห้ามคัดลอกกัน**
> — CONTRIBUTE ตอบว่า *แก้อะไรได้ ต้องขออนุญาตใครไหม กฎห้ามพลาดคืออะไร*
> หน้านี้ตอบว่า *แล้วมือต้องพิมพ์อะไร ตามลำดับไหน*
> เอกสารสองหน้าที่บอกเรื่องเดียวกันจะเพี้ยนกันเสมอ และโปรเจกต์นี้เคยเจ็บมาแล้ว

> **If you only want to fix a typo, you do not need this page at all.**
> Open the file on GitHub, click ✏️, type, press *Propose changes*. That is the
> whole workflow and it needs nothing installed. This page is for when you want
> to run the site on your own machine.

## ขั้น 0 — ติดตั้งครั้งเดียว (ครั้งแรกครั้งเดียวพอ)

### 0.1 เปิด Terminal

| เครื่อง | วิธีเปิด |
|---|---|
| **Mac** | กด `⌘ + Space` → พิมพ์ `Terminal` → Enter |
| **Windows** | กดปุ่ม Windows → พิมพ์ `Terminal` (หรือ `PowerShell`) → Enter |
| **VS Code** (ทั้งสองระบบ) | เมนู `Terminal` → `New Terminal` |

หน้าต่างที่ขึ้นมาจะมีบรรทัดที่รอให้พิมพ์ เรียกว่า *prompt* ตัวอย่างในหน้านี้จะเขียนแบบ
`$ คำสั่ง` — **`$` คือสัญลักษณ์ของ prompt ไม่ต้องพิมพ์ตาม** พิมพ์เฉพาะข้อความหลังจากนั้น

### 0.2 เช็กว่ามีของครบ

```bash
node -v     # ต้องขึ้น v22.x.x หรือใหม่กว่า
git --version
```

⚠️ **ต้องเป็น Node 22 ขึ้นไป** — Node 20 จะทำให้ `npm test` พังทันทีตั้งแต่บรรทัดแรก
(`supabase-js` ต้องการ WebSocket ที่ Node 20 ไม่มี) ถ้ายังไม่มี Node ให้ลงจาก
[nodejs.org](https://nodejs.org) เลือกตัว LTS

### 0.3 ล็อกอิน GitHub จาก Terminal

```bash
gh auth login          # เลือก GitHub.com → HTTPS → Login with a web browser
```

ถ้ายังไม่มีคำสั่ง `gh` ให้ลง [GitHub CLI](https://cli.github.com) ก่อน
(Mac: `brew install gh`) — ไม่ใช้ `gh` ก็ได้ แต่ทุกขั้นจะยาวขึ้นเพราะต้องสลับไปเว็บ

### 0.4 ดึงโปรเจกต์ลงเครื่อง

**เลือกทางเดียว** ตามว่าคุณถูกเพิ่มเข้าโปรเจกต์แล้วหรือยัง:

```bash
# ทาง A — ถ้าคุณเป็น collaborator (มีคนเชิญคุณเข้า repo แล้ว)
gh repo clone phuriphatma/samomdkkuweb

# ทาง B — ถ้าไม่ใช่ (ทางนี้คือค่าเริ่มต้น และไม่ต้องขอใคร)
gh repo fork phuriphatma/samomdkkuweb --clone
```

**ทาง B ใช้ได้กับทุกคนที่มีบัญชี GitHub ไม่ต้องรอใครเพิ่มสิทธิ์** GitHub จะสร้าง
สำเนาของโปรเจกต์ไว้ใต้ชื่อคุณ แล้ว `gh pr create` ยังเปิด pull request กลับมาที่นี่ได้เหมือนเดิม

**ความต่างจริง ๆ มีข้อเดียว: ทาง B ไม่ได้เว็บ preview อัตโนมัติ** เพราะ fork อ่านรหัสลับ
ของ repo ไม่ได้ตามการออกแบบของ GitHub ถ้าคุณจะแก้บ่อย ๆ ขอให้ผู้ดูแลเชิญเป็น
collaborator แล้วย้ายมาทาง A จะสบายกว่ามาก

```bash
cd samomdkkuweb
npm ci                 # ลง dependency ตาม package-lock.json เป๊ะ ๆ (ช้ากว่า npm i แต่ตรงกว่า)
```

### 0.5 ใส่ค่าเชื่อมฐานข้อมูล

ขอไฟล์ค่าตัวแปร (บล็อก `SUPABASE_DEV_*`) จากผู้ดูแล แล้วสร้างไฟล์ `.env.local`
ที่โฟลเดอร์บนสุดของโปรเจกต์ **ชี้ไปที่ `samo-dev` ซึ่งเป็นฐานข้อมูลสำหรับพัฒนา ไม่ใช่ของจริง**

⛔ **`.env.local` ห้ามขึ้น git เด็ดขาด** — มันอยู่ใน `.gitignore` อยู่แล้ว อย่าไปแก้
และ ⚠️ `samo-dev` เป็น**สำเนาข้อมูลจริงของนักศึกษา** (ตั้งใจให้เป็นแบบนั้น) กฎห้ามเปิดเผยข้อมูล
ใช้กับมันเท่ากับของจริงทุกประการ

### 0.6 เปิดเว็บบนเครื่องตัวเอง

```bash
npm run dev            # เปิด http://localhost:5174
```

เปิด browser ไปที่ `http://localhost:5174` **ถ้าเห็นเว็บสโมฯ ขึ้นมา ขั้น 0 จบแล้ว**
กด `Ctrl + C` ใน Terminal เพื่อหยุดเมื่อเลิกใช้

## ขั้น 1 — ทุกครั้งที่จะเริ่มงานใหม่: ดึงของล่าสุดก่อน

ตอนเปิด pull request จะชนกับงานคนอื่นเป็นกอง (merge conflict) การ pull ก่อนใช้เวลา 3 วินาที

## ขั้น 2 — สร้าง branch เสมอ ห้ามแก้บน `main`

### ต้องสร้าง branch ไหม? — **ต้อง ทุกครั้ง ไม่มีข้อยกเว้น**

ไม่ใช่เรื่องมารยาท แต่เป็นเรื่องกลไก: `main` ถูกล็อกไว้ (branch protection) —
push ตรงเข้าไปไม่ได้ ต้องผ่าน pull request เท่านั้น ถ้าคุณเผลอ commit บน `main`
ดูวิธีแก้ที่ **ขั้น 9.1** ข้างล่าง

```bash
git checkout -b ui/news-card-spacing
```

![main เป็นเส้นเดียวยาวตลอด แต่ละ branch แตกออกไปทำเรื่องเดียวแล้วรวมกลับเข้า main](./diagrams/branches.svg)

### ตั้งชื่อ branch ยังไง

`<ประเภท>/<เรื่องสั้น ๆ>` ภาษาอังกฤษ ตัวเล็ก ขีดกลางคั่น

| ขึ้นต้นด้วย | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| `feat/` | เพิ่มของใหม่ | `feat/dept-tool-golden-period` |
| `fix/` | แก้บั๊ก | `fix/vs-form-double-submit` |
| `ui/` | หน้าตา สี ระยะห่าง | `ui/news-card-spacing` |
| `docs/` | เอกสารอย่างเดียว | `docs/step-by-step` |

**ชื่อ branch มีผลจริง ไม่ใช่แค่ความสวยงาม** — เว็บ preview ของคุณจะใช้ชื่อนี้เป็นที่อยู่
`ui/news-card-spacing` จะกลายเป็น `https://ui-news-card-spacing.samomdkkuweb.pages.dev`
ตั้งชื่อสั้น ๆ แล้วอ่านง่ายไปด้วยกัน

**หนึ่ง branch = หนึ่งเรื่อง** อยากแก้สองเรื่องที่ไม่เกี่ยวกัน ให้แยกสอง branch สอง PR
— รีวิวเร็วกว่า และถ้าเรื่องหนึ่งมีปัญหา อีกเรื่องไม่ต้องรอ

## ขั้น 3 — แก้ แล้วดูผลทันที

เปิดอีกหน้าต่าง Terminal (หรืออีก tab) ทิ้งไว้:

```bash
npm run dev
```

แก้ไฟล์แล้ว **browser จะรีเฟรชเองทันที ไม่ต้องกดอะไร** แก้ไปดูไป

ไฟล์ไหนอยู่ตรงไหน ดูตาราง *File placement* ใน `CLAUDE.md` ที่โฟลเดอร์บนสุด
หรือสั้น ๆ: HTML อยู่ `src/html/` · CSS อยู่ `src/css/` · JS อยู่ `src/js/`

**ก่อนไปขั้นต่อไป เช็กสองคำสั่งนี้ให้เขียวก่อน** (CI จะรันซ้ำอยู่ดี รู้ตอนนี้เร็วกว่า):

```bash
npm test
npm run build
```

## ขั้น 4 — บันทึกงาน: `add` → `commit` → `push`

```bash
git status                       # ดูก่อนว่ามีอะไรเปลี่ยนบ้าง — ทำติดเป็นนิสัย
git add src/css/news.css         # เลือกเฉพาะไฟล์ที่ตั้งใจ
git commit -m "ui(news): ลดระยะห่างการ์ดข่าวบนมือถือ"
git push -u origin ui/news-card-spacing
```

### `git add .` ใช้ได้ไหม?

**ใช้ได้ แต่ให้ `git status` ก่อนทุกครั้ง** — `.` แปลว่า "ทุกอย่างที่เปลี่ยน" รวมถึงไฟล์ที่คุณ
ไม่ได้ตั้งใจ เช่นภาพหน้าจอที่เผลอเซฟไว้ในโฟลเดอร์โปรเจกต์ หรือไฟล์ทดลองที่ลืมลบ

⛔ **นี่คือจุดที่ข้อมูลนักศึกษาหลุดได้จริง** ชื่อ รหัสนักศึกษา อีเมล รูปถ่าย — repo นี้เปิด
สาธารณะ และ **ประวัติ git ลบไม่ได้จริง** ลบไฟล์พรุ่งนี้ ก็ยังย้อนดู commit วันนี้ได้
`git status` สามวินาที ป้องกันเรื่องที่แก้คืนไม่ได้

`-u origin <branch>` ใส่แค่ครั้งแรกของ branch นั้น หลังจากนั้น `git push` เปล่า ๆ พอ

## ขั้น 5 — เปิด Pull Request

```bash
gh pr create --fill --web
```

หรือถ้าเพิ่ง push แล้วเปิด GitHub ในเว็บ จะมีแถบเหลือง *Compare & pull request* ขึ้นให้กด

**เขียนในช่องคำอธิบายสามอย่าง** ไม่ต้องยาว:

1. **แก้อะไร** — หนึ่งประโยค
2. **ทำไม** — อาการเดิมเป็นยังไง
3. **ทดสอบยังไง** — จอกว้างเท่าไรบ้าง ปกติเช็ก 390 / 820 / 1280 px

> 📌 **ยังทำไม่เสร็จก็เปิด PR ได้** กด *Create draft pull request* แทน — คนอื่นเห็นว่าคุณ
> กำลังทำเรื่องนี้อยู่ จะได้ไม่ทำซ้ำกัน และคุณได้ CI กับ preview มาใช้ตั้งแต่ยังไม่เสร็จ
> ถ้าติดตรงไหน ใส่ `[help]` ไว้ในหัวข้อ

## ขั้น 6 — เว็บทดลอง (preview): ดูของจริงก่อนใครกดรับ

**ทุก branch ได้เว็บของตัวเองอัตโนมัติ** ลิงก์จะโผล่เป็นคอมเมนต์ใน pull request
ภายในไม่กี่นาที หรือถามจาก Terminal ได้เลย:

```bash
npm run preview:url
```

![สามสภาพแวดล้อม: เครื่องคุณและเว็บทดลองต่อฐานข้อมูล samo-dev ส่วนเว็บจริงต่อฐานข้อมูลจริง](./diagrams/environments.svg)

**เว็บทดลองต่อกับฐานข้อมูล `samo-dev` ไม่ใช่ของจริง** — กดปุ่ม ส่งฟอร์ม สร้างของทิ้ง
ได้เต็มที่ ไม่มีใครเดือดร้อน นี่คือที่ที่ควรทดสอบจริง ๆ ไม่ใช่แค่ดูบนเครื่องตัวเอง

ที่อยู่ preview **คงที่ตลอดอายุ branch** — bookmark ไว้ครั้งเดียว push ทีไรมันอัปเดตเอง
ส่งลิงก์นี้ให้เพื่อนในฝ่ายช่วยดูได้เลย เขาไม่ต้องลงอะไรทั้งนั้น

> **ถ้าคุณใช้ fork (ทาง B ในขั้น 0.4) จะไม่ได้ preview อัตโนมัติ** — เป็นข้อจำกัดด้าน
> ความปลอดภัยของ GitHub ไม่ใช่ความผิดคุณ ให้แนบภาพหน้าจอใน PR แทน หรือขอเป็น
> collaborator ถ้าจะแก้บ่อย

## ขั้น 7 — CI ตรวจ แล้วคนรีวิว

พอเปิด PR จะมีสามอย่างเกิดขึ้นเอง:

| เกิดอะไร | ใช้เวลา | ถ้าแดง |
|---|---|---|
| **build** — `npm test` + `npm run build` | ~2 นาที | กด *Details* อ่านบรรทัดแรกที่แดง แก้แล้ว push ทับ |
| **Cloudflare Pages** — สร้างเว็บทดลอง | ~2 นาที | มักหมายถึง build พังเหมือนกัน |
| **smoke** — เปิดเว็บทดลองด้วย browser จริง เช็กว่าไม่ตาย | ~1 นาที | หน้าเว็บโหลดขึ้นแต่ JS ไม่ทำงาน — ดู `docs/mistakes/frontend-ui.md` |

**แก้แล้วไม่ต้องเปิด PR ใหม่** commit เพิ่มแล้ว `git push` ทับ — PR เดิมอัปเดตเอง
ทุกอย่างรันใหม่ให้

### ใครต้องอนุมัติ

- **ทั่วไป** — collaborator คนไหนก็ได้หนึ่งคน
- **เส้นทางเปราะ** — `src/js/auth.js` · `src/js/db.js` · `src/js/notify.js` ·
  `src/js/uploads.js` · `supabase/` · `server/` · `appscript/` · `tools/` · `.github/`
  ต้องให้ **เจ้าของโปรเจกต์** อนุมัติ ระบบจะขอเอง คุณไม่ต้องไปตามใคร
  (`.github/CODEOWNERS` เป็นคนตัดสิน ไม่ใช่ดุลพินิจใคร)

**ถ้างานของคุณแตะรายการหลัง อย่าเพิ่งเขียนโค้ด** — เปิด draft PR เขียนย่อหน้าเดียวว่า
จะทำอะไรและทำไม แล้วรอความเห็นก่อน เร็วกว่าเขียนเสร็จแล้วมารื้อเยอะ

## ขั้น 8 — งานที่ต้องรองานอีกงาน (feature B ต้องรอ feature A)

**คำถามที่ถามกันบ่อยที่สุด และคำตอบคือ: ไม่ต้องรอ** มีสองทาง เลือกตามสถานการณ์

![สองทางเลือกเมื่องาน B ต้องรองาน A: แตก branch ซ้อนแล้ว rebase หรือรวม A เข้า main แบบยังเข้าไม่ถึง](./diagrams/dependent-features.svg)

### ทาง 1 — แตก branch ซ้อน (stacked branches)

ใช้เมื่อ **A ยังไม่ควรถูกรวม** เพราะยังไม่ผ่านรีวิว หรือยังไม่สมบูรณ์

```bash
git checkout feat/a               # ยืนบน branch ที่ยังรออยู่
git checkout -b feat/b            # แตก B ออกจาก A ไม่ใช่จาก main
# ทำงาน commit push ตามปกติ
```

ตอนเปิด PR ของ B **เปลี่ยน base branch เป็น `feat/a`** — บนหน้า GitHub มีปุ่ม *Edit*
ข้างหัวข้อ PR แล้วเลือก base ได้ ผลคือ diff ของ B จะแสดงเฉพาะงานของ B ไม่ปนงานของ A
(ถ้าไม่เปลี่ยน base คนรีวิวจะเห็นงานสองอันปนกันและอ่านไม่ออก)

**พอ A ถูกรวมเข้า `main` แล้ว** ให้ย้าย B มาต่อกับ `main`:

```bash
git checkout main && git pull origin main
git checkout feat/b
git rebase --onto main feat/a feat/b
git push --force-with-lease
```

`--force-with-lease` ไม่ใช่ `--force` — มันจะปฏิเสธถ้ามีคนอื่น push เข้า branch นี้ระหว่างนั้น
**force push ได้เฉพาะ branch ของคุณเอง ห้ามทำกับ `main` เด็ดขาด** (`main` ล็อกไว้อยู่แล้ว)

จากนั้นเปลี่ยน base ของ PR กลับเป็น `main` (GitHub มักเปลี่ยนให้เองเมื่อ A ถูกรวม)

### ทาง 2 — รวม A เข้า `main` ก่อน แต่ยังเข้าไม่ถึง

**ทางนี้ง่ายกว่ามาก และควรเป็นตัวเลือกแรกเสมอ** ถ้า A ไม่มีอะไรอันตราย

รวม A เข้า `main` ได้เลย แค่ทำให้มันยัง**เข้าไม่ถึง** — ไม่ใส่ลิงก์ในเมนู หรือซ่อนหลัง
สิทธิ์ที่ยังไม่มีใครถือ แล้ว B ก็แตกจาก `main` ตามปกติ ไม่มี rebase ไม่มีอะไรซ้อน

**ที่ทางนี้ปลอดภัย เพราะ "รวม ≠ ขึ้นเว็บจริง"** — งานที่อยู่ใน `main` ยังไม่ถึงมือนักศึกษา
จนกว่าผู้ดูแลจะสั่ง deploy จุดตรวจที่แท้จริงอยู่ตรงนั้น การกดรับ PR จึงถูกและถอยกลับได้

### ⛔ อย่ารอ

การกอง commit ไว้ใน branch เดียวเพราะ "รอ A ก่อน" คือทางที่แพงที่สุด — branch ยิ่งอยู่นาน
ยิ่งชนกับงานคนอื่น และ PR ที่ใหญ่จนอ่านไม่ไหวคือ PR ที่ไม่มีใครรีวิว

## ขั้น 9 — เจอปัญหาแบบนี้ทำยังไง

### 9.1 เผลอ commit บน `main`

ยังไม่ได้ push — ย้าย commit ไป branch ใหม่ได้ครบ:

```bash
git branch fix/my-work          # ทำเครื่องหมายไว้ตรงที่ยืนอยู่
git reset --hard origin/main    # ถอย main กลับ (งานไม่หาย อยู่ใน branch แล้ว)
git checkout fix/my-work
```

⚠️ `reset --hard` ลบสิ่งที่ยังไม่ commit ทิ้ง — `git status` ให้ว่างก่อนพิมพ์บรรทัดนั้น

### 9.2 PR ขึ้นว่า "This branch is out-of-date"

มีคนรวมงานเข้า `main` หลังคุณแตก branch:

```bash
git checkout main && git pull origin main
git checkout ui/news-card-spacing
git merge main                  # แก้ conflict ถ้ามี แล้ว commit
git push
```

### 9.3 Merge conflict

git จะเขียนเครื่องหมายไว้ในไฟล์แบบนี้:

```
<<<<<<< HEAD
บรรทัดที่มีอยู่ใน main
=======
บรรทัดที่คุณเขียน
>>>>>>> ui/news-card-spacing
```

เปิดไฟล์ ตัดสินใจว่าจะเอาแบบไหน (หรือผสม) **ลบทั้งสามบรรทัดเครื่องหมายออกให้หมด**
แล้ว `git add <ไฟล์>` และ `git commit`

`git status` จะบอกว่ายังเหลือไฟล์ไหนที่ยังไม่แก้

### 9.4 CI แดงแต่บนเครื่องเขียว

เกือบทุกครั้งคือ Node คนละรุ่น (`node -v` ต้อง 22+) หรือลืม `git add` ไฟล์ใหม่เข้าไป
— `git status` แล้วดูว่ามีไฟล์ค้างอยู่ใต้ *Untracked files* ไหม

### 9.5 เว็บ preview ไม่ขึ้น

- ยังสร้างไม่เสร็จ — รออีกสองสามนาที
- คุณใช้ fork — fork ไม่ได้ preview ตามการออกแบบ (ขั้น 6)
- build พัง — ดูที่ check *build* ใน PR

## ขั้น 11 — หลังถูกรวมแล้ว: ขึ้นเว็บจริงเมื่อไร

**รวมเข้า `main` แล้วยังไม่ขึ้นเว็บจริง** เจ้าของโปรเจกต์ต้องต่อ VPN ของ มข.
แล้วสั่ง deploy ไปที่เครื่อง VM อีกครั้ง — ปกติจะรวบหลาย PR แล้ว deploy ทีเดียว
เพราะแต่ละครั้งใช้เวลาประมาณ 90 วินาที

การออกแบบให้เป็นแบบนี้ตั้งใจ: **กดรับ PR จึงเป็นเรื่องถูกและถอยกลับได้** จุดตรวจที่จริงจัง
อยู่ที่ deploy จุดเดียว ไม่ใช่กระจายไปขวางทุกคนตอนรีวิว
